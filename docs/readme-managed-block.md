# Managed blocks — a devkit-owned region inside a user-editable file

Covers `README.md` (task #9) and `CLAUDE.md` (task #40, §6). Same markers, same splice,
same handling of a file that carries no markers at all.

**Status:** BUILT (task #9, 2026-07-09). Makes the generated brain's `README.md` a
**hybrid**: a devkit-owned region the upgrader keeps current, wrapped by user-owned space
the upgrader never touches. Shipped: the golden/template README carries the markers around
its body (inert HTML comments), and `tools/update_brain.py` **splices** the fresh devkit
body into the existing brain's markers instead of clobbering the whole file. Locked in by
hermetic CI gates (`tools/check_readme_block.py` = gate 8; `tools/check_claude_block.py` =
gate 16). Markers used (ASCII, so the
`update_brain` constants match byte-for-byte):

```
<!-- BEGIN generated by second-brain-devkit: do not edit inside; regenerated by update_brain.py. Put your own notes outside these markers. -->
<!-- END generated by second-brain-devkit -->
```

> **Extended to `CLAUDE.md` by task #40 — DONE 2026-07-28**, which also revisited what a
> **marker-less** file should mean. §1's original answer — hand off forever, in silence — is
> now the *reporting* half only: both files are **adoptable**, named loudly on every run and
> brought under management by an opt-in `--adopt` that keeps the existing file verbatim.
> §4's "No markers → devkit hands off entirely" and §3's "skip it (leave user-owned)" are
> superseded on the reporting point; the never-write-without-consent rule stands. See §6.

## 0. The problem (observed 2026-07-07)

The generated brain's `README.md` is **devkit-owned**: `update_brain.py` re-emits it from
`template/` **wholesale** (it was in the re-emit list, *not* the `PRESERVE` list of
`vault/ data/ config/ CLAUDE.md GEMINI.md` — `CLAUDE.md` left that list in #40, §6). So any
edit a user makes to the brain README is **silently clobbered** on the next
`update_brain --apply`.

This bit us for real: a `~/second-brain` README had a hand-added "planned retrieval-quality
summary" — which was both (a) misplaced devkit-roadmap content, and (b) fated to be
overwritten anyway. The lesson isn't only "that content was misplaced"; it's that the brain
README has **no place for the user at all**, which is surprising for the front-page doc of
a repo they own.

## 1. The design — a marked managed block

Wrap the devkit's README content in HTML-comment markers; let the user own everything
outside them:

```markdown
<!-- Personal notes, links, TODOs — the user owns this; the devkit never touches it. -->

<!-- BEGIN generated by second-brain-devkit — do not edit inside; regenerated on update -->
… the devkit's operational README (Setup → Everyday use → Layout → …) …
<!-- END generated by second-brain-devkit -->

<!-- More user space below, equally untouched. -->
```

- **Devkit content lives *between* the markers; the user writes *above or below*.**
- **Create and update unify.** The `template/` README already ships **with** the markers
  around the devkit body. Initial create copies the file whole (user regions empty). A
  later `update_brain` **splices** the fresh devkit body between the *existing* file's
  markers, preserving the user's preamble/appendix byte-for-byte.
- **Opt-out by deleting the start marker.** If `BEGIN` is absent (the user removed it to
  take full ownership), the upgrader implants **nothing** and leaves the README alone —
  the same "detect + instruct, never force" stance as `install_skill.py` / `doctor.py`.
- **Markers are inert.** HTML comments don't render in Markdown / Obsidian, so there's no
  visible clutter.

This is the devkit's established **managed-block pattern**, generalized to the brain
README — the same shape as `install_skill.py --nudge`'s marked block in `~/.claude/
CLAUDE.md`, the `ai-project-status` block in the devkit's own `CLAUDE.md`, and the
`related_auto:` block in the [auto-linking design](auto-linking.md) (task #8).

## 2. Contract

- Editing **inside** the managed region is **not** preserved — that region is the devkit's,
  and `update_brain` overwrites it. The `BEGIN` comment says so inline. User content goes
  **outside** the markers.
- `update_brain` still reports the README under NEW / CHANGED / preserved so a dry-run
  shows exactly what the splice would change.

## 3. Implementation sketch

- **Golden first** (per the build loop): add the markers to the golden `README.md`, then
  `vendor_golden.py` → rebuild `template/`. The markers are just comments, so the
  structural-diff oracle and the brain's `self_test` are unaffected (still byte-exact).
- **`update_brain.py`**: replace the wholesale README copy with a splice —
  `existing.preamble + START + template.body + END + existing.appendix`. On a target whose
  README lacks `BEGIN`/`END`, skip it (leave user-owned) and say so in the report.
- **Guard the malformed case**: `BEGIN` without `END` (or vice-versa) → skip + warn rather
  than guess a boundary.
- **`create_second_brain.py`** is unchanged — it copies the template README verbatim, which
  already contains the markers with empty user regions.

## 4. Edge cases

- **No markers** (user deleted them) → devkit hands off entirely.
- **Only one marker present** → skip + warn (don't guess).
- **User edited inside the region** → overwritten by design; the inline notice + dry-run
  preview are the mitigation.
- **Multiple BEGIN/END pairs** → v1 supports exactly one managed region; reject extras.

## 5. Relationship to other work

- Resolves the README-ownership tension surfaced during the task-#6 dogfooding.
- Same **managed-block** primitive as [auto-linking](auto-linking.md) (task #8) — both
  build on the shared **splice-a-marked-block helper (task #10)**, done first so this logic
  isn't duplicated.
- Purely local-first; no bearing on big-brain. Sits **before** Postgres/Approach B.

Build loop unchanged: prototype in the golden → `vendor_golden.py` → rebuild `template/`
→ `tools/ci.py` green.

## 6. `CLAUDE.md` — the same block, one different answer (task #40, DONE 2026-07-28)

**The bug.** `update_brain` refreshed tooling but listed `CLAUDE.md` in `PRESERVE_FILES`,
so a brain created before a feature took the *code* and never the *prose that says the code
exists*. Found by dogfooding #39: `~/second-brain` accepted the embed-excluded tooling
cleanly, then had to have its `CLAUDE.md` hand-edited to learn the convention — and a
feature nobody is told about does not get used.

**Why it stayed invisible.** Newly generated brains were always fine — `CLAUDE.md` is a
`cleaned` manifest entry, so it *is* emitted. Every generate-from-scratch check passed. Only
a real, upgraded brain was missing the docs, and nothing in CI upgraded a brain. That is the
shape worth remembering: **a create path and an upgrade path that disagree, with tests only
on the create path.**

**What shipped.** Identical markers, identical splice — and, after one course correction,
identical handling of a marker-less file.

The first cut made only `CLAUDE.md` adoptable, reasoning that a stale README is at least
*visible* to the human reading it. **Dogfooding killed that distinction within the hour.**
The real brain's README was 142 lines behind and missing an entire feature section, and
**absence is invisible to a reader too** — you cannot see prose that was never written. Both
files are now adoptable on the same terms. The lesson generalises past this repo: *"a human
will notice"* is only a safeguard against **wrong** content, never against **missing**
content.

`--adopt` is opt-in because a marker-less file has two indistinguishable causes — the brain
predates managed blocks, or the user deliberately deleted the markers to take ownership. The
report names both readings and offers the way back; someone in the second camp simply never
passes the flag. Adoption writes the devkit block **first** (an agent reads top-down, so
current directives must precede the copy they supersede) and keeps the user's previous file
verbatim below a notice telling them to prune.

**That preserve-don't-replace choice was immediately vindicated.** Adopting the real brain
turned up a `<!-- task-system:begin -->` block in its `CLAUDE.md` — a genuine local
customisation the devkit body knows nothing about. A wholesale replace, or a "looks like the
old default, safe to overwrite" heuristic, would have deleted it silently.

**Two smaller things it forced:**

- **The sign-off was lying.** Reporting the gap and then printing `✅ already up to date`
  restores exactly the silence the feature exists to end. An unmanaged adoptable file now
  ends the run with a warning instead. Gate 16 asserts the string is absent.
- **The template must be a fixed point of its own splice.** An extra blank line before the
  `END` marker (added for readability) made a *pristine* brain report as CHANGED forever,
  because `splice_block` regenerates that region without it. Gate 8 caught it. The emitted
  layout is whatever the splice produces — not whatever reads best.

**Closed — `vault/templates/new-note.md` (2026-08-03).** It duplicates the note gate that
**gate 9** requires to match `CLAUDE.md`, but it sat under the preserved `vault/`, so an upgrade
could leave a brain violating a build-time invariant. First shipped as a *report*; that was
half a fix. It is now the **one named exception** to "never write into `vault/`" (`VAULT_OWNED`
in `update_brain.py`) and is refreshed wholesale on every upgrade.

Why a carve-out rather than relaxing the rule: the file is devkit-owned in everything but
location. It lives in the vault only because that is where Obsidian's **Templates plugin** can
insert from — moving it out would break the editor workflow it exists for — and it is not a
note (`templates/` is not a PARA root, so it is never embedded, searched, or returned by
`get_note`). Naming one path keeps the promise auditable: *"this tool writes exactly one file
inside your vault, and here it is"*, rather than degrading to *"it might write anywhere in
there."* Gate 16 asserts both halves — the template refreshes, **and** a real note beside it
survives untouched.

A splice of just the marked region was considered and rejected: it would protect user
customisation of a file no user customises, at the cost of more machinery. Wholesale overwrite,
with the dry run showing CHANGED first, is the same deal every other tooling file gets.

Gate: `tools/check_claude_block.py` (`ci.py` 16/16) — splice preserves user space, idempotent,
marker-less is named and left alone, `--adopt` loses nothing and leaves the brain genuinely
managed, half-marked is refused, note-template drift is reported and `vault/` is never written.
